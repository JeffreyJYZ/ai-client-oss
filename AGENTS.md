# ai-client-oss

Tauri desktop app (`oss-ai-client`) with a Vite + React 19 (TS) frontend. Bun + Biome (root `biome.jsonc`).

## Layout

- `web/` — frontend *and* its own `package.json`/`bun.lock`. Run every web command from here.
- `web/src-tauri/` — Rust shell (`tauri.conf.json`, `Cargo.toml`); Tauri `beforeDevCommand`/`beforeBuildCommand` = `bun run dev` / `bun run build`.
- `web/src/` — all frontend source.
- `android/`, `ios/` at repo root — empty placeholders, not real mobile output.
- License: **GPL-3.0-only** (`LICENSE` + `web/src-tauri/Cargo.toml` `license`, `web/package.json`). The 0.1.x releases were MIT and stay MIT (grants irrevocable); never claim released versions are GPL.

## Search

- **`rg`, always scoped to a path — never `grep`, and never the `grep` tool.** The `grep` alias excludes `.git`/VCS but not `node_modules`, so an unscoped recursive grep walks all deps. Scope it (`rg <pat> web/src`) or exclude (`rg -g '!node_modules' <pat> .`). **Never `find`/`fd` from `$HOME` or `/`** — every tool a lane needs is on `PATH`, and a bare broad scan burns a core for minutes against the user's files (2026-10-19: a lane ran `find` over the home dir).

## Fonts

- **System stacks only — never bundle font files.** Font home is `web/src/ui/fonts.css` (`--sans/--heading/--mono/--rounded/--serif` on `:root`); `web/src/App.css` consumes them (`html { font-family: var(--mono) }`).
- Apple faces from CSS generics: `ui-sans-serif`→SF Pro, `ui-monospace`→SF Mono, `ui-rounded`→SF Pro Rounded, `ui-serif`→New York (all variable; italic via `font-style`). Non-Apple falls back to native UI font.
- **No `@font-face`/`url()` font assets, never self-host Apple SF** — SF license forbids embedding/redistribution/derivatives. Full license detail in global `AGENTS.md`.

## Tailwind

- Tailwind **v4** via `@tailwindcss/vite` (devDeps in `web/`). No PostCSS; CSS entry `web/src/App.css` (`@import "tailwindcss";` first, above `ui/fonts.css`). Theme via `@theme` in CSS.
- `web/tailwind.config.mjs` exists **only for editor IntelliSense** (Zed/VS Code) — v4 auto-detects content; Vite ignores the file. Never `@config` it unless real theme moves there.
- `biome.jsonc` sets `css.parser.tailwindDirectives: true` so Biome parses `@theme`/`@apply`/`@utility`.

## UI

- **Settings sections fold with plain `<details>`/`<summary>`; never put an `onClick` on the summary that calls `preventDefault`.** A control in the heading row is the activation target, so the section won't fold on its own — and `preventDefault` also cancels that control's own activation, silently making heading checkboxes untickable (shipped 0.2.0). Both halves browser-verified.

## Linting

- **Effect checking = two layers, both wired.** Biome GritQL is syntactic (no types); the Effect language service is type-aware.
- **Biome GritQL:** `biome-plugins/*.grit` ban `async`/`await`/`throw`/`try-catch`/`new Promise`. Wired in `biome.jsonc` `plugins`, each scoped `"includes": ["**/web/src/**"]` — the glob **needs the leading `**/`** (`web/src/**` **silently** matches nothing). Suppress per line: `// biome-ignore lint/plugin/<rule>: reason` (used for `main.tsx`'s bootstrap throw).
- **`@biomejs/biome` is a `web` devDependency, pinned exactly to the `biome.jsonc` `$schema` version** — `lint`/`fix` call bare `biome`, which resolves only if installed. A global `~/.bun/bin/biome` hides the omission; the release workflow's `beforeBuildCommand` (`bun run build`) then dies `biome: command not found` (exit 127). Pinned (not `^`) because a formatter bump can reformat the whole tree.
- **Effect language service:** `@effect/language-service` in `web/tsconfig.app.json` `compilerOptions.plugins`. Headless: `bunx effect-language-service diagnostics --project tsconfig.app.json --format text` (catches `floatingEffect`, `missingEffectContext`, `missingReturnYieldStar`; exits 1 on findings). Wired into `web` `lint` — `biome check . && effect-language-service diagnostics --project tsconfig.app.json` — so `build` runs it. For CI/`tsc`: `effect-language-service patch`. Add rules: `effect-language-service config`.
- **Gotcha:** Biome `correctness/useYield` errors on a trivial `Effect.gen(function* () { return x })` with no `yield*` — use `Effect.succeed`/`Effect.sync` for no-yield effects.
- **Gotcha:** callback-based Web APIs (`FileReader`, `IDBRequest`) with `Effect.tryPromise` need a raw `new Promise`, which `no-new-promise.grit` bans — use `Effect.callback` (see `lib/db/web.ts`, `ui/Composer.tsx`). A typed `new Promise<T>()` slips past the plugin (evades rather than fixes — don't).
- **Gotcha:** Biome lints files Vercel generates. `static-build` writes `.vercel/static-build/package-manifest.json` into the build root, `biome check .` flags it, and `bun run build` fails → every deployment errors (visible only in the Vercel build log). `biome.jsonc` `files.includes` excludes `**/.vercel`, and `web/.gitignore` lists `.vercel`.
- **Gotcha:** a script or test importing `@lib/*` (or `@/*`) resolves through `web/tsconfig.json`'s root `paths` (aliases live there, not only in `tsconfig.app.json`, because that config is solution-style and bun reads only the root one) — no symlink needed. Fallback: `ln -sfn ../src/lib web/node_modules/@lib` (node_modules gitignored), run from `web/`.
- **Gotcha:** with TS 6+, `bun:test` types are not implicit — tests need `@types/bun` (web/) **and** `"bun"` in `web/tsconfig.app.json` `types` (`["vite/client", "bun"]`), or every test file fails `tsc` on its `bun:test` import. Never add an `exclude` for `**/*.test.ts` to a tsconfig — it greens `tsc` by typechecking no tests. Prove wiring with a scratch `.test.ts` carrying a deliberate type error — `tsc -b` must fail.
- **Verifying a network feature in a browser**: override `window.fetch` *in the page* for the feature's constant hostnames only, passing all other requests through (else model calls break); pair a mock model endpoint logging each request body; seed `localStorage["ai-client.settings"]` before reload. Logged bodies are the evidence — a marker/rendered reply are not. Settings persist only on change; a boot writes nothing, so a hand-built seed must be the whole object or zod defaults. Recipe: toggle a control once to persist the real shape, patch that object, reload. A heading control needs its precondition (web-search box `disabled` until the active provider is search-capable). A desktop-only path is provable in a browser with `agent-browser open --init-script <file>`: stub `window.__TAURI_INTERNALS__` before modules evaluate (module-level read; a stub set after load is ignored), answer `plugin:app|version` with a version and reject the updater command so `findUpdate` falls to the real GitHub API. Trap: that stub selects the Tauri db adapter whose IPC rejects, so `setSettings` silently does not persist and a dismissal looks lost on reload though it's fine in the real app. The stub is committed at `scripts/desktop-stub.js` (arbitrary version, mocked `api.github.com`); reuse for comparable runs and never load it from a bun test (`isDesktop`/db adapter chosen at module load leaks desktop mode into later suites order-dependently).

## Testing

- **Never `mock.module` a *project* module; third-party only, never two competing fakes.** `mock.module` replaces a namespace entirely and process-wide — bun 1.4.2 shares one module registry across test files and `mock.restore()` does not reset it (reproduced), so `mock.module("@lib/db", () => ({ db }))` left later files with `db` mocked and `Settings`/`web`/`SETTINGS_KEY` undefined, order-dependently (bun discovery unsorted → passes local, breaks in CI or on file add). Import the real module and drive it directly; inject the seam. One shared third-party stub (`web/src/lib/db/__test-support__/fake-invoke.ts`) is used by every db suite — a file there must not match `*.test.ts`.
- **`cd web && bun run verify` is the single gate** (`tsc -b && biome check . && effect-language-service diagnostics --project tsconfig.app.json && bun test`). Use it, not pieces. Covers `web/` only — repo-root `scripts/` (`build-plugins.ts`, `build-docs.ts`, `bump-version.ts`, `verify-release.ts`) sit outside `tsc -b`/`biome check`, so load-bearing logic there is proven only by hand: move the pure part into `web/src` and test it, or give it its own check. The plugin build's chunk no-imports guard did this — `web/src/lib/build/bareImports.ts` + test, imported by `scripts/build-plugins.ts`; the build-time throw stays in the script.
- **zod v4 takes `z.ZodType<Output, Input>` — there is no `ZodTypeDef`** (v3's three-arg form is a `TS2724`). A *broken* annotation still drives inference, so it surfaces as `unknown`/`{}` errors in **other** files while `bun test` stays green (bun strips types); only `tsc -b` shows it. When a schema field gains a default, the annotation must widen its **input** (`z.ZodType<MemoryEntry, unknown>`) or the annotation itself is the type error.
- **Docs reference gates: hold the whole curated surface, not the entry list.** `entries.ts` `referenceEntries` returns `[sdk.ts]` alone once `sdk.ts` exists, and the artifact is generated from that same file, so an export-vs-artifact comparison shrinks both sides together (delete `export *`, re-run `bun run docs`, all green). `reference.test.ts` therefore has a separate subset check over every `surfaceModules` entry. Likewise `surface.ts` `summarise` keeps the whole doc comment — the sentence-boundary fallback applies only past `DESCRIPTION_CAP`; first-sentence-only dropped every second paragraph (the provider `buildRequest` idempotence note). A truncated description ending in `…` fails the suite.
- **Fixtures must not contain key-shaped strings.** GitHub push protection rejects the whole push (`GH013`, naming commit + path) for any string matching a provider key pattern, and it scans commits, so one in an unpushed commit means rewriting history, not a fixup — the branch stays unpushed until the blob is gone. Use obvious placeholders (`fixture-openrouter-key-not-real`, `fixture-tinyfish-key-not-real`); tests only need the field non-empty. A block is a pattern match, not proof of a leak: compare hashes against the real stores without printing values (`~/Library/Application Support/land.jyz.aiclient/settings.json`, key env vars) — a fixture string matching nothing there is fabricated, which is what happened here.
- **`main.tsx`'s bootstrap is the one allowed top-level `await`.** The desktop host must read its version via Tauri IPC (`runningVersion()` is `Effect.tryPromise`), so the entry awaits `runtime.runPromise(...)` before `createRoot` — and the Grit `no-await` plugin fires on it, suppressed by one documented `biome-ignore`. That carve-out is the rule's gap, not the code's. **Removing the await blanks the entire desktop app**: `Effect.runSync` cannot run a promise-backed effect (`AsyncFiberError`, thrown before `createRoot`), and because web mode takes the synchronous branch every web-mode browser proof passes while the shipped platform is dead. **Anything calling the sync registry bridges must run after that await** — `plugins/providers.ts`'s `protocolNames`/`resolveProviderSync` are `runtime.runSync`, so a module-scope or import-time call throws `AsyncFiberError` on desktop only; reachable routes: a new entry point (worker, second binary, a test exercising `state/chat.ts` without the runtime), a boot-order change, or a plugin `setup` before boot.
- **A browser proof of a plugin example clicks the palette's `<button>`, never its `<li>`** — the row's handler lives on the button, so `li.click()` runs nothing and only closes the palette (measured 2026-10-19). **And never assert on `document.body.textContent` with an install textarea on screen**: the pasted plugin source sits in the DOM, so "the surface rendered" passes with every surface closed. Assert on a structural selector (the example's own class list) and check the closed state too.

- **Prove a mock leak with a probe, not an order-run** — bun treats positional args as **filters** over its own discovery order, so `bun test a b` and `bun test b a` are *one* run and prove nothing; show the poison directly instead (a mock installed by one file makes a sibling's `import { Settings } from "@lib/db"` fail), and treat a green suite as evidence neither way.

## Plugin system

- **A locked set guarantees an entry stays *registered*; reachability is separate and untested by default.** `app.shell` owned the only `ui.root.layout` and `app.settings` the only `settings.root.shell`, so with both off the Plugins manager was registered and unreachable — measured: bare preset left `#root` at 0 chars. Both are now locked where the route renders: the container (locked `app.substrate`) renders `ui/MinimalHost.tsx` when the root slot is empty (the manager mounted directly plus what's off), and the settings surface `settings.root.shell` rides `app.substrate` too (hosts every section incl. the manager, part of the way back; sections stay `app.settings`'). **Still open (design's):** a plugin-contributed `ui.root.layout` rendering no `settings.root` shows the manager nowhere — the plugin owns the UI. A test must assert the reachable target, never that something rendered; adding an area (P2's `app.memory`) can repeat the split exactly.

- **An area toggle must gate every surface of that area's feature — never only its UI and its tools.** Measured on `app.memory`: with the area switched off and `memoriesEnabled` still true, the turn loop kept **injecting** the memory block and kept **storing** notes the user could no longer see, because the injection and the persistence read the *setting*, not the area. When you add an area, enumerate its surfaces — UI, registry entries, prompt injection, persistence, background work — and gate each one on the area; a toggle that leaves a surface live is a hardcoded feature wearing a switch.
- **`host.run(effect)` forks work into the caller's scope** — the correct way for a plugin or built-in area to start long-lived work: the fibre is a child of that scope, so closing it (disable, reload, area toggle) interrupts it, and an interruption is re-raised while other causes are logged as `PluginFault`. Before, only `Effect.runFork` existed, discarding the fibre — which is how each `app.themes` reconcile leaked one subscription to an unbounded `PubSub`. **And `Effect.runFork` is `runForkWith(Context.empty())`:** a `Logger` the caller passed through `Effect.provide` **never reaches forked work**, and a forked log line lands on the console only, never in the plugin log — so capture a forked log with a console spy, not with a provided `Logger` layer (measured in P2's T6, where a scratch test proved the provided logger saw nothing).

- **Plugins are full-trust, in-process, unsandboxed.** `plugin-data` is the only capability enforced for real (path-scoped in Rust); `net` is unenforceable (webview has global `fetch`); the rest consent-only. Never describe it as a sandbox; user-facing truth in `lib/plugins/consent.ts` (re-exports `docs/notes.ts`'s per-capability table — one home, gated by `docs/reference.test.ts`). **Keep each caveat attached to its claim, never let a compressed list imply a boundary:** the author guide's `native` row once listed `http` under `plugin-data`'s path scope, inverting the model while obeying the letter — `http` rides the unenforceable `net` and is "a convenience, never a gate" (`services.ts`).

- **A plugin is one pre-built ES module with no imports.** Source may `import` React / `react/jsx-runtime` (preset rewrites onto `__aiClientReact`/`__aiClientJsxRuntime`) and any other bare specifier (bundled); the emitted chunk must import nothing — `scripts/build-plugins.ts` fails the build and `moduleImport.ts` refuses a bare specifier at load. Host globals are exactly `__aiClient` (the `Host`), `__aiClientReact`, `__aiClientJsxRuntime` (`lib/plugins/globals.ts`). Never `import` a host module from a plugin: the plugin build has no `@lib` alias, so a value import does not resolve and the build fails (never silently bundles), and even bundled it'd be a second copy whose module state (e.g. `themes.ts`'s app service) isn't the app's. A type-only `import type { … } from "@lib/plugins/sdk"` is supported: erased at build, how examples get `Host`/`Tool`/`CommandDefinition`.

- **Build then install — never HMR.** `bun scripts/build-plugins.ts [<id>…]` → `web/public/plugins/<id>/main.js` (gitignored, as is `web/dist`). Prove plugins against the **production bundle** (`cd web && bunx vite build && bunx vite preview`): a pasted/installed plugin's source is imported from a Blob (production path only), while `vite dev` imports the built asset URL instead, so an installed plugin cannot be exercised under dev. Examples + author guide: `web/plugins/`.

- **Two-way isolation is the contract, both halves load-bearing.** A plugin fault must never take the app down: `ContributionBoundary` wraps every contribution, pipeline stages fail-open (logged, disabled for the session, input unchanged), `executeTool` turns a faulting executor into a failed outcome. A slot migration must stay DOM-identical: one `<Slot>`/`useComponent` per region, no wrapper, empty slot renders nothing — plugins off, the DOM equals pre-plugin-system.

- **The slot map is `lib/plugins/ids.ts` `slotIds`** (one `as const` tuple → `z.enum` schema *and* union type; the generated reference page renders it). Adding a slot is one line there plus one `<Slot id>` in the tree. A *component* id (`ui.markdown`) resolves through `useComponent`, not a `<Slot>`.

- **`host.tools.register` announces a tool by registering it — its registry entry *is* its enablement.** The outgoing body's `tools` is assembled by `requestTools` (`lib/providers/presets.ts`) from the endpoint's web-search declaration and host policy (`fetch_url`, TinyFish client `web_search` keep their stored toggle) plus the tools registry, read in the host request path (`state/chat.ts`'s `registeredToolDeclarations`); policy-owned names are dropped so a built-in is declared once. Assembly is idempotent because `buildRequest` re-runs in `SendMsg` each tool round (replayed as `prev` with `skipUserMessage`) and must rebuild the same `tools`. A `transformBody` stage cannot add one — `buildRequest` overwrites it.

- **No Effect runner is exposed to a plugin** — `host.chat.send`/`storage`/`native`/`notify.confirm`/`themes.apply` all return `Effect`s. The working route (used by the examples) is `import { Effect } from "effect"` in the plugin source: the preset bundles it (a second copy, ~90 kB) and it runs effects the host built with its own copy. Add a `host.run` before telling authors to bundle Effect.

- **One theme core, many facades — identity is the invariant, not behaviour.** `makeThemeService`'s core is built once in `HostLayer`, carried as `HostServices.themesService`; `makeHost` gives each plugin `themesService.forPlugin(<that plugin's registry view>)`, so every plugin's `apply`/`clear`/`active` is the app's, over one `<style>` element (`ai-client-theme`) and one `data-theme` marker. A second core means a second stylesheet — never construct one outside `HostLayer`.

- **`host.ui.kit` is a curated re-export, by identity, of `@/ui/kit` + `@/ui/Markdown`** (`lib/plugins/kit.ts`'s one module-level `pluginKit`, typed `PluginKit`; `sdk.ts` exports it and `docs/entries.ts` lists it). An explicit list, not `export *`, keeps the plugin-facing subset deliberate — a kit addition for the app's own use does not silently become plugin API.

- **Reload is two-phase: `preparePlugin` (decode/inspect/import) → close the old scope → `activatePlugin` (run the new `setup`).** A bad import leaves the old instance running; old `dispose` runs before new `setup`, so it can't retract what the new setup applied. **Deliberate semantic change:** a `setup` that throws leaves nothing loaded (`status: "failed"`, logged, `attempted` recorded so the settle loop doesn't retry) — old already closed, so a failed reload never runs old code behind a new manifest. The host owns only what a plugin registered plus its `setup` handle, so a plugin mirroring state must retract it in `dispose` and re-apply in `setup`; contributions are absent for one synchronous stretch between close and activate.

- **The plugin database has one owner.** `lib/plugins/source/web.ts` declares `DB_NAME`/`DB_VERSION`/`PLUGIN_STORE` and holds the single cached connection (`pluginDatabase`; only a successful open is cached, so an unreadable store stays retryable) — the write half (`install.ts`) imports it rather than opening a second. A swallowed `list` read failure is recorded to the plugin log (`recordLog` + console), because a version mismatch previously listed as nothing installed, silently.

- **`planOf` is pure, and a decision is recorded only as its step is about to run.** A plan the settle loop's round bound never reaches therefore leaves no trace: those decisions stay outstanding and the next `settle` (any settings change) retries them. Never record `attempted` or consume `forced` at plan time, or an unrun decision looks already-tried.

- **`"plugin-changed"` is defined twice — `runtime.ts` `PLUGIN_CHANGED_EVENT` and `src-tauri/src/lib.rs` — with no shared source; `runtime.test.ts` pins them by reading the Rust constant.** A drift makes the desktop watcher's listener never fire, silently.

## Providers

- **OpenCode Go (`oc go`) is NOT callable from the app's webview — two independent server-side blockers.** (1) Its chat endpoint 404s the CORS `OPTIONS` preflight (no `access-control-allow-origin`) while `/models` on the same host answers `acao=*`, so a webview refuses the preflighted POST and WebKit reports `TypeError: Load failed` — reads as an app bug, isn't. (2) It requires `x-opencode-session` before auth (absent → `MissingSessionID`; present → `Go requires a credential`), and the app has no per-provider custom-header setting. Docs: one base for every Go family — `https://opencode.ai/inference/go/v1` — the family being the method path (`/chat/completions` | `/messages` | `/responses`), so no per-family split; our preset conforms. Neither `/zen/go/v1` nor the path was ever the user-visible cause (it also answers; the 404 is the preflight). `listModels` stays on the webview `fetch` on purpose (a GET whose preflight answers 200 with `Authorization` allowed) while `chat_stream` is POST-only; the session header is omitted there because it isn't an allowed header. Supported routes: a local gateway that is a validated client (the CLI's `http://127.0.0.1:8787/w/opencode/…`) or the native streaming transport — never the webview's `fetch`.

## Web search

- **OpenRouter search = the `openrouter:web_search` server tool, never the `web` plugin.** OpenRouter deprecated the plugin (`plugins:[{id:"web"}]`, or a `model:…:online` suffix) because it searches once per request — every single message, so a bare "nice" became a query for the city of Nice. The server tool lives in `tools` (`{type:"openrouter:web_search",parameters:{max_results}}`), lets the model decide whether to search (0–N times), and works on `/responses` as well as `/chat/completions`.
- `searchTools(search, tools)` in `web/src/lib/providers/presets.ts` maps a `SearchSpec` to the endpoint's declaration (OpenAI → `web_search_preview`; OpenRouter → the server tool); `searchKindFor(baseUrl)` decides which endpoints have a mechanism at all. The persisted `ProviderConfig.tools` array is only the on/off + result-count carrier. An endpoint with no mechanism gets **neither** key — never a phantom tool the model cannot execute.

- **Long-term memory is notes, not a tool loop — but the tool path now exists.** Global notes live in `Settings.memories` (ride the backup); the model records one by ending its reply with `<memory>…</memory>`, which `lib/memory.ts` strips before display/storage (pure, idempotent, safe mid-stream — visible text always derived from the whole raw accumulation) and `state/chat.ts` persists after the run guard, injecting `memoryPrompt` into the outgoing system prompt **only**. A client tool-execution loop exists (`chat.ts` turns a completed `tool_call` into `executeTool` + a correlated result, no orphans; T24a declares registered tools on the wire) — so a tool-call design is available; earlier text claiming otherwise predates it. `SendCtx.tools` is still only the search declaration.

## Tauri / native

- **Desktop chat streams through the shell, not the webview** (`t25`): `chat_stream` / `chat_stream_cancel` (an ipc `Channel`, status first then ordered text runs, abort on drop) behind one transport abstraction selected by `isDesktop` at the single chat fetch site — so a provider whose chat endpoint a webview cannot call (OpenCode Go preflight) works on desktop, in order, cancellably. The shared SSE parser is untouched, so web behaviour unchanged. `x-opencode-session` is sent for `opencode.ai` hosts only (value = conversation id, for routing/prompt caching). Known gap: `Test connection` (`lib/providers/models.ts`) still webview-fetches; the probe is the one path not yet on the transport.

- **App-defined `#[tauri::command]`s are NOT ACL-gated — `capabilities/default.json` needs no entry.** Proven two ways (T20 review): `db_set_settings`/`db_list_conversations` run from the desktop webview with no `db_*` entry in `capabilities` and no `web/src-tauri/permissions/` dir (settings + conversations exist on disk), and pinned Tauri 2.12.2 rejects an app command only when `has_app_acl_manifest` is true or the origin is non-local. **Forward risk: shipping the app's own `permissions/` manifest gating every app command — a missing entry then fails on desktop only while every browser stub passes.** Only plugin permissions are ACL-gated.
- **Plugin native commands = `web/src-tauri/src/lib.rs`: nine (`plugin_{list,read_file,write_file,remove,data_dir}` + `plugin_fs_{read,write,list,delete}`), all through one scope helper (`resolve_within` + `safe_id`).** `plugin-data/<id>` is the **only enforced** capability; `net` is unenforceable; the rest consent-only. Never call it a sandbox.
- **Two real containment traps, both fixed once and both easy to reintroduce.** (1) `PathBuf::join`/`push` **discards the base** when the pushed path has a *prefix* (Windows `C:`), so a plugin `id` must be an **allowlist** (`[A-Za-z0-9._-]+`), never a denylist of `/ \ . ..` — mirrored in `manifestSchema.id` so a bad id fails at install. (2) Re-appending a **non-existent** suffix is not safe by itself: a *dangling* symlink makes `canonicalize` return `NotFound`, the walk treats it as a plain name and returns the symlink, and the write follows it out of the root — so check `symlink_metadata` per re-appended component.
- `resolve_within` `create_dir_all`s the root, so a *read* command creates the dir; and a `rel_path` of `""`/`"."`/`"subdir/.."` resolves to the root itself (a whole-dir delete is the plugin's own dir). Documented, not guarded.

- **Branch worktrees from `origin/main`, never the bare `main` ref** — local `main` is checked out in `/Users/jyz/dev/monorepos/ai-client-oss` and never advances when a release or `HEAD:main` push moves the remote, so `git worktree add … -b <name> main` silently bases lanes on the last release (measured 2026-10-19: four lanes started at 0.5.0). `origin/main` is the only current ref here.

## Release & CI

- **Version home = `web/src-tauri/tauri.conf.json` `version`** (Tauri reads it for the bundle). **A new feature is still a *patch* unless the user names the bump** — `minor` is their call, never inferred from "this feels like a feature" (2026-10-19: shipped 0.7.0 for plugin examples, was told "NOT 0.7.0 WHY MINOR", and had to withdraw it). **And every release needs its own go-ahead**, even the same session that approved the previous one. Recovering from a wrong bump: `gh release delete <tag> --yes --cleanup-tag`, then bump *down* explicitly (`bun scripts/bump-version.ts <x.y.z>` accepts a literal), `bun run docs`, commit, and merge the withdrawn remote bump with `-s ours` so the lower version wins; the tag push then builds. `bun scripts/bump-version.ts <patch|minor|major|X.Y.Z>` rewrites it plus `web/src-tauri/Cargo.toml`, `web/src-tauri/Cargo.lock` (`[[package]] name = "app"`) and `web/package.json`, by targeted text replacement (never re-serialize — the JSON files are tab-indented). Runs from the repo root; `--root <dir>` overrides for tests. **A hand-bump must be followed by `bun run docs`**: `docs/reference.test.ts` pins the committed reference's `appVersion` to `web/package.json`, so the artifact is stale (and `verify` red) until regenerated — `build`/CI regenerate it, and the release workflow's `version` job now does it too (a web install + `(cd web && bun run docs)` before its `git add`). Without that the workflow left the default branch red on its own bump commit and failed CI, which is why 0.4.0 shipped by **tag push** instead of `workflow_dispatch`.
- **LF only** — `.gitattributes` pins `* text=auto eol=lf`. GitHub's Windows runner checks out CRLF (`core.autocrlf=true`), which made Biome diff every line and failed `bun run lint` in the release build (only the Windows job sees it).
- **Updater signing keypair — the private key IS the ability to ship updates.** Private `~/.tauri/ai-client.key` + its password `~/.tauri/ai-client.key.password` (both `600`, local only); repo secrets `TAURI_SIGNING_PRIVATE_KEY` (the key *content*, not a path) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the *public* key sits in `tauri.conf.json` `plugins.updater.pubkey` (safe to share, never regenerated once shipped — a new key orphans every installed app, since the pubkey is baked into the binary that verifies the download). Never print the private key or password, never write either into a repo file. Verify the embedded pubkey against `~/.tauri/ai-client.key.pub`. In-app updating shipped in 0.1.2 (0.1.0 and 0.1.1 have no updater and must be replaced by hand); the first genuine update was proven end to end: an installed 0.1.2 replaced itself with 0.2.0 in place.
- **The updater's platform key is written by tauri-action, not the CLI.** The CLI only makes the `.app.tar.gz` + `.sig`; `tauri-action`'s `upload-version-json` writes `latest.json`, mapping `macos`→`darwin`, `arm64`→`aarch64`, and a universal build publishes `darwin-aarch64`/`darwin-x86_64` (plus their `-app` variants). So pass **no `target`** to `check()`: the plugin resolves `{os}-{arch}-{installer}` then `{os}-{arch}`, and both slices already match. The docs' `macos-universal` is a custom string for a self-hosted endpoint, not what GitHub Releases carries (`updaterJsonKeepUniversal` is what would add a universal key). Android/iOS are unsupported by this plugin.
- **Release creation needs the repository's default workflow permissions set to `write`** (Settings → Actions → General). With the default at `read`, tauri-action's `POST /releases` returned `Resource not accessible by integration` even though the workflow declares `permissions: contents: write`. A run's token permissions are fixed when the run starts, so a **re-run cannot pick up a settings change — push a fresh run (delete + re-push the tag)**. `ci.yml` still pins `permissions: contents: read` for itself.
- **A `desktop-v*` tag need not be on `main`** — 0.3.0 was cut from `plugin-system` and published all three platforms; the tap follows **releases**, not `main`. So release-without-merge is supported, and a tag is the unit of release.
- **Release = `.github/workflows/release-tauri.yml`.** `workflow_dispatch` (input `bump` = patch|minor|major) runs a `version` job that bumps, commits, pushes `main`, tags `desktop-v<version>`, then builds; a `desktop-v*` **tag push** builds only (never re-point a tag once its release is published — asset names and the release derive from it; the build job fails if the tag ≠ `tauri.conf.json`). Matrix: `macos-latest` (universal, `--target universal-apple-darwin`), `ubuntu-22.04`, `windows-latest` → `tauri-apps/tauri-action@v0` creates the GitHub Release and uploads installers.
- **Verify a published release with `bun scripts/verify-release.ts [version]`.** The version defaults to `tauri.conf.json` and the repo is read from the git remote; it polls (default 40 × 20s) because publishing is async. It checks what `gh release view` cannot: every installer suffix present; a `.sig` beside each updater artefact (a run before signing secrets existed uploads unsigned archives no client accepts); `/releases/latest` actually being the new tag; a fetchable `latest.json`; and an entry with a signature **and a live artefact URL** for each of `darwin-aarch64`/`darwin-x86_64`/`linux-x86_64`/`windows-x86_64` — a platform with no entry never updates, silently. Exit 0 verified, 1 failed/timeout, 2 usage.
- **Builds are unsigned and not notarized — "right-click → Open" does NOT work on current macOS (user-confirmed on 27); it restricts unsigned apps further.** The only reliable install path: clear the download quarantine flag `xattr -dr com.apple.quarantine "/Applications/oss-ai-client.app"`. On Windows, SmartScreen → **More info → Run anyway**. The release body carries both — never document right-click → Open again.
- **`ubuntu-*` Tauri jobs need the apt list:** `libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev` (it is `libayatana-…`, not `libappindicator3-dev`). GitHub migrates `ubuntu-latest` to Ubuntu 26 on 2026-10-19 — if that job's apt list starts failing, the image change is why.
- **CI = `.github/workflows/ci.yml`** (push to `main` + PRs): a `web` job (tsc, biome, effect-LS, vite build — each its own step, non-zero fails the job) and a `rust` job (`cargo check --all-targets` with the apt list).
- `web/package.json` `lint` = `biome check . && effect-language-service …` — **`&&`, never `;`** (`;` swallows Biome's exit code, so the gate stops gating). CI runs the four web steps explicitly rather than `bun run lint`.
- App identifier is `land.jyz.aiclient`, **not** the Tauri default `com.tauri.dev` — it owns the app-data dir, so changing it orphans stored conversations.
- Website (non-Tauri) build shows a desktop download link: `web/src/constants/links.ts` + `isDesktop` from `web/src/lib/platform.ts` (same `__TAURI_INTERNALS__` probe `lib/db/index.ts` uses). Vercel project `ai-client-oss-site` (team jeffreys-projects-b51c8adf, Git-connected to `main`, Root Directory `web`). **`vercel ls <project>` prints nothing in a non-interactive shell** (its table needs a TTY) — a poll loop spins forever; check a deployment with `vercel inspect <url>` or `GET /v3/deployments/<id>` (`/events?builds=1` has the build log), with the CLI token from `~/Library/Application Support/com.vercel.cli/auth.json`.
- **Favicons: raster (PNG + `.ico`), never SVG-only.** Brave with **Standard Shields** and nothing blocked won't display an SVG favicon — Chrome shows it, and a fresh-profile Brave even fetches it (200), it just never appears in the tab; dropping the SVG for PNGs fixed it. `index.html` declares `/favicon-32.png`, `/favicon-256.png`, `/favicon.ico`, `/apple-touch-icon.png`, each with `?v=N` — **bump `?v=` whenever an icon file changes** (a browser holds a favicon per origin and won't refresh it; brave-browser#53451). Verify the server side with `agent-browser connect <port>` against a headless Brave/Chrome on a fresh `--user-data-dir` + `network requests`. `/favicon.svg` is only the artwork source, not declared. **Rasterize with `bun scripts/build-icons.ts`** (`resvg`, brew) — **never `qlmanage`**, which flattens the mark onto white (that's what put white corners on the first raster set; an alpha *channel* (`sips -g hasAlpha`) doesn't prove transparency — only pixels sampled through a canvas do). `web/src-tauri/icons/*` came from that same `qlmanage` raster, so the desktop/dock icon carried the same white corners until `resvg -w 1024 -h 1024 web/public/favicon.svg web/src-tauri/app-icon.png` + `(cd web && bunx tauri icon src-tauri/app-icon.png)` regenerated the set. **`scripts/build-icons.ts` now emits `app-icon.png` itself**, inset to Apple's grid (about 824 of 1024) by widening the viewBox, because full-bleed art is right for a favicon but reads oversized in the Dock; every platform size derives from that one file via `tauri icon`. **Changing `icons/` does not make cargo rebuild** — `tauri dev` reuses the stale binary, so the Dock keeps the old mark until a rebuild (touch a source file or `cargo clean -p app`), and `killall Dock` if the icon cache sticks.
- **A white screen right after a push is usually the mid-deploy window, not a code fault.** The edge briefly serves the new `index.html` before its JS asset is live, so the module 404s, React never mounts, and the page is blank white (the app applies no background until it does); it clears on reload. **Check before touching code**: `agent-browser errors` against the live origin, and `document.getElementById("root")?.children.length`. `agent-browser` also has `console`.
- **The Homebrew cask lives in `JeffreyJYZ/homebrew-tap` (`Casks/oss-ai-client.rb`), and the tap repins itself.** The app self-updates, so the cask only points at the newest release: `.github/workflows/bump-cask.yml` in the tap runs on a schedule, reads this repo's newest `desktop-v*` release, downloads the universal dmg, digests it, commits version + sha256. No cross-repo token and no step in this repo's release (it only writes its own repo). `auto_updates true` keeps Homebrew from comparing versions, so the in-app updater keeps working and `brew upgrade` never overwrites a self-updated app; Homebrew's receipt can lag the running version after one of those updates, which is cosmetic (the pin follows releases anyway, so even a forced reinstall lands the current version). Two things users meet: casks from a third-party tap are refused until `brew trust jeffreyjyz/tap` (once per machine; casks can run code, formulae don't), and these unsigned builds still get quarantined on install, which Gatekeeper refuses, so the cask clears that attribute itself in the `postflight_steps` form — Homebrew 7 has no `--no-quarantine` flag. **An app already in `/Applications` from the dmg or the in-app updater also blocks the cask: Homebrew refuses to overwrite what it doesn't own (`It seems there is already an App at …`), so moving to the cask needs `brew install --cask --force`, which replaces a same-or-older bundle and leaves Application Support alone.**
- **Never ship a UI change tested only on the dev server** — run the production bundle (`bunx vite build && bunx vite preview`). Dev serves unbundled ESM and cannot catch bundling faults. **And never revert on a guess**: an unnecessary revert once cost a working feature, because the blame was assigned to the newest commit instead of being tested.
- Validate a workflow locally with `actionlint .github/workflows/*.yml` (brew).
- **Local macOS `bunx tauri build` dies at the DMG step** (`error running bundle_dmg.sh`) — Tauri's `bundle_dmg.sh` runs a Finder AppleScript to prettify the window, which hangs without a GUI/Automation session. Prefix `CI=true` (Tauri then passes `--skip-jenkins`, skipping it), or build `--bundles app` to skip DMGs entirely. GitHub runners export `CI=true` already, and the release workflow pins it on the tauri-action step.
