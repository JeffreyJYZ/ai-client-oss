# ai-client-oss

Tauri desktop app (`oss-ai-client`) with a Vite + React 19 (TS) frontend. Bun + Biome (root `biome.jsonc`).

## Layout

- `web/` — the frontend *and* its own `package.json`/`bun.lock`. Run every web command from here.
- `web/src-tauri/` — Rust shell (`tauri.conf.json`, `Cargo.toml`); Tauri `beforeDevCommand`/`beforeBuildCommand` = `bun run dev` / `bun run build`.
- `web/src/` — all frontend source.
- `android/`, `ios/` at repo root — empty placeholders, not real mobile output.
- License: **GPL-3.0-only** (`LICENSE` + `web/src-tauri/Cargo.toml` `license`, and `web/package.json`). The published **0.1.x releases were MIT and stay MIT** — those grants are irrevocable, so never claim the released versions are GPL.

## Search

- **`rg`, always scoped to a path — never `grep`.** Neither a bare `grep -r` nor the `grep` tool: the shell's `grep` alias excludes `.git` and VCS dirs but **not** `node_modules`, the bulk of this tree, so an unscoped recursive grep walks every dependency and returns their matches as if they were yours. Scope it (`rg <pat> web/src`) or exclude the tree (`rg -g '!node_modules' <pat> .`).

## Fonts

- **System stacks only — never bundle font files.** Sole font home is `web/src/ui/fonts.css` (`--sans/--heading/--mono/--rounded/--serif` on `:root`); the CSS entry `web/src/App.css` consumes them (`html { font-family: var(--mono) }`).
- Apple faces come from the CSS generics, not a file: `ui-sans-serif`→SF Pro, `ui-monospace`→SF Mono, `ui-rounded`→SF Pro Rounded, `ui-serif`→New York (all variable; italic via `font-style`). Non-Apple OS falls back to its native UI font.
- **No `@font-face`/`url()` font assets, and never self-host Apple SF** — the SF license forbids embedding, redistribution and derivative works. Full license + system-font detail in the global `AGENTS.md`.

## Tailwind

- Tailwind **v4** via `@tailwindcss/vite` (devDeps in `web/`). No PostCSS config; CSS entry is `web/src/App.css` (`@import "tailwindcss";` first, above `ui/fonts.css`). Theme goes in CSS via `@theme`.
- `web/tailwind.config.mjs` exists **only for editor IntelliSense** (Zed / VS Code LSP) — v4 auto-detects content and the Vite plugin ignores the file. Never `@config` it from CSS unless real theme moves there.
- `biome.jsonc` sets `css.parser.tailwindDirectives: true` so Biome parses `@theme`/`@apply`/`@utility`.

## UI

- **Settings sections fold with plain `<details>`/`<summary>`; never put an `onClick` on the summary that calls `preventDefault`.** A control in the heading row (checkbox, button) is the click's activation target, so the section never folds on its own — and `preventDefault` cancels the control's own activation too, which silently made heading checkboxes untickable (shipped in 0.2.0). Both halves browser-verified.

## Linting

- **Effect checking = two layers, both wired.** Biome GritQL plugins are syntactic (no types); the Effect language service is type-aware.
- **Biome GritQL:** `biome-plugins/*.grit` ban `async`/`await`/`throw`/`try-catch`/`new Promise`. Wired in `biome.jsonc` `plugins`, each scoped `"includes": ["**/web/src/**"]` — the glob **needs the leading `**/`** (`web/src/**` silently matches nothing). Suppress per line: `// biome-ignore lint/plugin/<rule>: reason` (used for `main.tsx`'s bootstrap throw).
- **`@biomejs/biome` is a `web` devDependency, pinned exactly to the `biome.jsonc` `$schema` version** — the `lint`/`fix` scripts call bare `biome`, which resolves only if it is installed. Locally a global `~/.bun/bin/biome` hides the omission; the release workflow's `beforeBuildCommand` (`bun run build`) then dies `biome: command not found` (exit 127). Pinned (not `^`) because a formatter bump can reformat the whole tree.
- **Effect language service:** `@effect/language-service` in `web/tsconfig.app.json` `compilerOptions.plugins`. Headless: `bunx effect-language-service diagnostics --project tsconfig.app.json --format text` (catches `floatingEffect`, `missingEffectContext`, `missingReturnYieldStar`; exits 1 on findings). Wired into `web` `lint` — `biome check . && effect-language-service diagnostics --project tsconfig.app.json` — so `build` runs it too. For CI/`tsc`: `effect-language-service patch`. Add rules: `effect-language-service config`.
- **Gotcha:** Biome `correctness/useYield` errors on a trivial `Effect.gen(function* () { return x })` with no `yield*` — use `Effect.succeed`/`Effect.sync` for no-yield effects.
- **Gotcha:** callback-based Web APIs (`FileReader`, `IDBRequest`) with `Effect.tryPromise` need a raw `new Promise`, which `no-new-promise.grit` bans — use `Effect.callback` (see `lib/db/web.ts`, `ui/Composer.tsx`). A typed `new Promise<T>()` slips past the plugin's pattern (evades rather than fixes — don't).
- **Gotcha:** Biome lints files **Vercel generates**. The `static-build` step writes `.vercel/static-build/package-manifest.json` into the build root, `biome check .` flags it, and `bun run build` fails → **every deployment Errors** (visible only in the Vercel build log, never locally). `biome.jsonc` `files.includes` excludes `**/.vercel`, and `web/.gitignore` lists `.vercel`.
- **Gotcha:** a script or test importing `@lib/*` (or `@/*`) resolves through `web/tsconfig.json`'s root `paths` (the four aliases live there, not only in `tsconfig.app.json`, because that config is solution-style and bun reads only the root one) — no symlink needed. Fallback if a tool still bypasses the root config: `ln -sfn ../src/lib web/node_modules/@lib` (node_modules is gitignored), then run from `web/`.
- **Gotcha:** with TypeScript 6+, `bun:test` types are not implicit — tests need the `@types/bun` devDependency (`web/`) **and** `"bun"` in `web/tsconfig.app.json`'s `types` (`["vite/client", "bun"]`), or every test file fails `tsc` on its `bun:test` import. **Never add an `exclude` for `**/*.test.ts`** to a tsconfig project: it greens `tsc` by typechecking no test at all. Prove the wiring with a scratch `.test.ts` carrying a deliberate type error — `tsc -b` must fail.
- **Verifying a network feature in a browser** (the pattern every tool-loop proof used): override `window.fetch` *in the page* for the feature's constant hostnames **only**, passing every other request through, or the app's own model calls break; pair it with a mock model endpoint that logs every request body it receives, and seed settings into `localStorage["ai-client.settings"]` before reloading. Then the logged bodies are the evidence for what actually reached the wire — a marker and a rendered reply are not. **Settings reach `localStorage` only when they change — a boot writes nothing, so a hand-built seed must be the whole object or zod falls back to defaults.** The reliable recipe: toggle a control once so the real shape persists, patch that object, reload. A heading control also needs its precondition met before it proves anything (the web-search box is `disabled` until the active provider is search-capable). **A desktop-only path is provable in a browser with `agent-browser open --init-script <file>`**: stub `window.__TAURI_INTERNALS__` there so `isDesktop` is true before the modules evaluate (it is a module-level read, so a stub set after load is ignored), answering `plugin:app|version` with a version and rejecting the updater command so `findUpdate` falls through to the real GitHub API. Trap: with that stub present the Tauri db adapter is selected and its IPC rejects, so `setSettings` silently does not persist and a dismissal looks lost on reload although it is fine in the real app. **The stub itself is committed — `scripts/desktop-stub.js`** (arbitrary version, mocked `api.github.com`) — reuse it so a before/after run stays comparable, and never load it from a bun test: `isDesktop` and the db adapter are chosen at module load, so it would leak desktop mode into later suites order-dependently.

## Testing

- **Never `mock.module` a *project* module; third-party modules only, and never two competing fakes for one module.** `mock.module` replaces a namespace **entirely** and **process-wide** — bun 1.4.2 shares one module registry across test files and `mock.restore()` does not reset it (reproduced with probes), so `mock.module("@lib/db", () => ({ db }))` left every file loaded after it with `db` mocked and `Settings`/`web`/`SETTINGS_KEY` **undefined**, order-dependently (bun's discovery order is not sorted, so it passes locally and breaks in CI or when a file is added). Import the real module and drive it directly; inject the seam instead. One shared third-party stub (`web/src/lib/db/__test-support__/fake-invoke.ts`) is used by every db suite — a file there must not match `*.test.ts`.
- **`cd web && bun run verify` is the single gate command** (`tsc -b && biome check . && effect-language-service diagnostics --project tsconfig.app.json && bun test`). Use it, not the pieces. **It covers `web/` only** — the repo-root `scripts/` (`build-plugins.ts`, `build-docs.ts`, `bump-version.ts`, `verify-release.ts`) is outside both `tsc -b` and `biome check`, so any load-bearing logic there (a guard, a generator, a verifier) is proven only by whoever ran it by hand: move the pure part into `web/src` and test it there, or give it its own check. The plugin build's chunk no-imports guard did exactly that — `web/src/lib/build/bareImports.ts` + its test, imported by `scripts/build-plugins.ts`; the build-time throw stays in the script.
- **Docs reference gates: hold the whole curated surface, not the entry list.** `entries.ts`'s `referenceEntries` returns `[sdk.ts]` alone once `sdk.ts` exists, and the artifact is generated from that same file — so an export-vs-artifact comparison shrinks both sides together (delete an `export *`, re-run `bun run docs`, all green). `reference.test.ts` therefore has a separate subset check over every `surfaceModules` entry. Similarly `surface.ts`'s `summarise` keeps the **whole** doc comment — the sentence-boundary fallback applies only past `DESCRIPTION_CAP`; the old first-sentence-only behaviour silently dropped every second paragraph (the provider `buildRequest` idempotence note). A truncated description ending in `…` fails the suite.
- **Fixtures must not contain key-shaped strings.** GitHub push protection rejects the **whole push** (`GH013`, naming the commit + path) for any string matching a provider's key pattern, and it scans the *commits*, so one in an unpushed commit means rewriting history, not adding a fixup — the branch stays unpushed until the blob is gone. Use obvious placeholders (`fixture-openrouter-key-not-real`, `fixture-tinyfish-key-not-real`); the tests only need the field non-empty. A block is a **pattern** match, not proof of a leak: compare hashes against the real stores without printing values (`~/Library/Application Support/land.jyz.aiclient/settings.json`, the key env vars) — a fixture string matching nothing there is fabricated, which is what happened here.
- **`main.tsx`'s bootstrap is the one allowed top-level `await`.** The desktop host must read its version through Tauri IPC (`runningVersion()` is `Effect.tryPromise`), so the entry awaits `runtime.runPromise(...)` before `createRoot` — and the Grit `no-await` plugin fires on it, suppressed by one documented `biome-ignore`. That entry-file carve-out is the rule's gap, not the code's. **Removing the await blanks the entire desktop app**: `Effect.runSync` cannot run a promise-backed effect (`AsyncFiberError`, thrown before `createRoot`), and because web mode takes the synchronous branch every web-mode browser proof passes while the shipped platform is dead. **Anything calling the sync registry bridges must therefore run after that await** — `plugins/providers.ts`'s `protocolNames`/`resolveProviderSync` are `runtime.runSync`, so a module-scope or import-time call throws `AsyncFiberError` **on desktop only**; the reachable routes are a new entry point (worker, second binary, a test exercising `state/chat.ts` without booting the runtime), a boot-order change, or a plugin `setup` running before boot.
- **Prove a mock leak with a probe, not an order-run** — bun treats positional args as **filters** over its own discovery order, so `bun test a b` and `bun test b a` are *one* run and prove nothing; show the poison directly instead (a mock installed by one file makes a sibling's `import { Settings } from "@lib/db"` fail), and treat a green suite as evidence neither way.

## Plugin system

- **Plugins are full-trust, in-process, unsandboxed.** `plugin-data` is the only capability enforced for real (path-scoped in Rust); `net` is **unenforceable** (the webview has global `fetch`); the rest are consent-only. Never describe any of it as a sandbox; the user-facing truth lives in `lib/plugins/consent.ts` (which re-exports `docs/notes.ts`'s per-capability table — one home, gated by `docs/reference.test.ts`). **Keep each caveat attached to its claim, and never let a compressed list imply a boundary:** the author guide's `native` row once listed `http` under `plugin-data`'s path scope, inverting the model while obeying the letter of this rule — `http` rides the unenforceable `net` and is "a convenience, never a gate" (`services.ts`).

- **A plugin is one pre-built ES module with no imports.** Source may `import` React / `react/jsx-runtime` (the preset rewrites them onto `__aiClientReact`/`__aiClientJsxRuntime`) and any other bare specifier (bundled in); the **emitted** chunk must import nothing — `scripts/build-plugins.ts` fails the build and `moduleImport.ts` refuses a bare specifier at load. Host globals are exactly `__aiClient` (the `Host`), `__aiClientReact`, `__aiClientJsxRuntime` (`lib/plugins/globals.ts`). Never `import` a host module from a plugin: the plugin build runs with no `@lib` alias, so a **value** import does not resolve at all and **the build fails** — it never silently bundles — and even bundled it would be a second copy whose module state (e.g. `themes.ts`'s app service) is not the app's. A **type-only** `import type { … } from "@lib/plugins/sdk"` **is** supported: it is erased at build time and is how the examples get `Host`/`Tool`/`CommandDefinition`.

- **Build then install — never HMR.** `bun scripts/build-plugins.ts [<id>…]` → `web/public/plugins/<id>/main.js` (gitignored, as is `web/dist`). Prove plugins against the **production bundle** (`cd web && bunx vite build && bunx vite preview`): a pasted/installed plugin's source is imported from a Blob (production path only), while `vite dev` imports the built asset URL instead, so an installed plugin cannot be exercised under dev. Examples + author guide: `web/plugins/`.

- **Two-way isolation is the contract, and both halves are load-bearing.** A plugin fault must never take the app down: `ContributionBoundary` wraps every contribution, pipeline stages are fail-open (logged, disabled for the session, input unchanged), `executeTool` turns a faulting executor into a failed outcome. And a slot migration must stay **DOM-identical**: one `<Slot>`/`useComponent` per region, no wrapper element added, an empty slot rendering nothing — with plugins off the DOM equals what it was before the plugin system existed.

- **The slot map is `lib/plugins/ids.ts` `slotIds`** (one `as const` tuple → `z.enum` schema *and* union type; the generated reference page renders it). Adding a slot is one line there plus one `<Slot id>` in the tree. A *component* id (`ui.markdown`) resolves through `useComponent`, not a `<Slot>`.

- **`host.tools.register` announces a tool by registering it — its registry entry *is* its enablement.** The outgoing body's `tools` is assembled by `requestTools` (`lib/providers/presets.ts`) from the endpoint's web-search declaration and host policy (`fetch_url`, TinyFish's client-side `web_search` — those keep their stored toggle) plus the tools registry, read in the host's request path (`state/chat.ts`'s `registeredToolDeclarations`); policy-owned names are dropped so a built-in is declared once. The assembly is **idempotent** because `buildRequest` re-runs inside `SendMsg` on every tool round (replayed as `prev` with `skipUserMessage`) and must rebuild the same `tools`. A `transformBody` stage cannot add one — `buildRequest` overwrites it.

- **No Effect runner is exposed to a plugin** — `host.chat.send`/`storage`/`native`/`notify.confirm`/`themes.apply` all return `Effect`s. The working route (used by the examples) is `import { Effect } from "effect"` in the plugin source: the preset bundles it (a second copy, ~90 kB) and it runs effects the host built with its own copy. Add a `host.run` before telling authors to bundle Effect.

- **One theme core, many facades — identity is the invariant, not behaviour.** `makeThemeService`'s core is built once in `HostLayer`, carried as `HostServices.themesService`; `makeHost` gives each plugin `themesService.forPlugin(<that plugin's registry view>)`, so every plugin's `apply`/`clear`/`active` is the app's, over one `<style>` element (`ai-client-theme`) and one `data-theme` marker. A second core means a second stylesheet — never construct one outside `HostLayer`.

- **`host.ui.kit` is a curated re-export, by identity, of `@/ui/kit` + `@/ui/Markdown`** (`lib/plugins/kit.ts`'s one module-level `pluginKit`, typed `PluginKit`; `sdk.ts` exports it and `docs/entries.ts` lists it). An explicit list, not `export *`, keeps the plugin-facing subset deliberate — a kit addition for the app's own use does not silently become plugin API.

- **Reload is two-phase: `preparePlugin` (decode/inspect/import) → close the old scope → `activatePlugin` (run the new `setup`).** A bad import leaves the old instance running untouched; the old `dispose` runs before the new `setup`, so it cannot retract what the new setup applied. **Deliberate semantic change:** a `setup` that throws leaves *nothing* loaded (`status: "failed"`, logged, `attempted` recorded so the settle loop does not retry) — the old instance is already closed, so a failed reload can never run old code behind a new manifest's name. The host owns only what a plugin registered plus its `setup` handle, so a plugin mirroring state onto the page must retract it in `dispose` and re-apply it in `setup`; the contributions are absent for one synchronous stretch between close and activate.

- **The plugin database has one owner.** `lib/plugins/source/web.ts` declares `DB_NAME`/`DB_VERSION`/`PLUGIN_STORE` and holds the single cached connection (`pluginDatabase`; only a *successful* open is cached, so an unreadable store stays retryable) — the write half (`install.ts`) imports it rather than opening a second. A swallowed `list` read failure is recorded to the plugin log (`recordLog` + console), because a version mismatch previously listed as **nothing installed**, silently.

- **`planOf` is pure, and a decision is recorded only as its step is about to run.** A plan the settle loop's round bound never reaches therefore leaves no trace: those decisions stay outstanding and the next `settle` (any settings change) retries them. Never record `attempted` or consume `forced` at plan time, or an unrun decision looks already-tried.

- **`"plugin-changed"` is defined twice — `runtime.ts` `PLUGIN_CHANGED_EVENT` and `src-tauri/src/lib.rs` — with no shared source; `runtime.test.ts` pins them by reading the Rust constant.** A drift makes the desktop watcher's listener never fire, silently.

## Providers

- **OpenCode Go (`oc go`) is NOT callable from the app's webview — two independent blockers, both server-side.** (1) Its **chat** endpoint 404s the CORS `OPTIONS` preflight (no `access-control-allow-origin`) while `/models` on the same host answers `acao=*`, so a webview refuses to send the preflighted POST and WebKit reports `TypeError: Load failed` — a diagnosis that reads as an app bug and is not. (2) It requires **`x-opencode-session` before auth** (absent → `MissingSessionID`; present → `Go requires a credential`), and the app has no per-provider custom-header setting. Docs: **one** base for every Go family — `https://opencode.ai/inference/go/v1` — the family being the **method path** (`/chat/completions` | `/messages` | `/responses`), so there is **no per-family split**; our preset now conforms to that. **Neither `/zen/go/v1` nor the path was ever the user-visible cause** (it also answers; the 404 is the preflight). **`listModels` stays on the webview `fetch` on purpose** — a GET whose preflight answers 200 with `Authorization` allowed — while `chat_stream` is POST-only; the session header is omitted there because it is not an allowed header. The supported route is a **local gateway** that is a validated client (the CLI's own `http://127.0.0.1:8787/w/opencode/…`), or the **native streaming transport** — never the webview's `fetch`.

## Web search

- **OpenRouter search = the `openrouter:web_search` server tool, never the `web` plugin.** OpenRouter **deprecated** the plugin (`plugins:[{id:"web"}]`, or a `model:…:online` suffix) because it **searches once per request** — every single message, so a bare "nice" became a query for the city of Nice. The server tool lives in `tools` (`{type:"openrouter:web_search",parameters:{max_results}}`), lets the **model** decide whether to search (0–N times), and works on `/responses` as well as `/chat/completions`.
- `searchTools(search, tools)` in `web/src/lib/providers/presets.ts` maps a `SearchSpec` to the endpoint's declaration (OpenAI → `web_search_preview`; OpenRouter → the server tool); `searchKindFor(baseUrl)` decides which endpoints have a mechanism at all. The persisted `ProviderConfig.tools` array is only the on/off + result-count carrier. An endpoint with no mechanism gets **neither** key — never a phantom tool the model cannot execute.

- **Long-term memory is notes, not a tool loop — but the tool path now exists.** Global notes live in `Settings.memories` (so they ride the backup); the model records one by ending its reply with a `<memory>…</memory>` tag, which `lib/memory.ts` strips before display/storage (pure, idempotent, safe mid-stream — the visible text is always derived from the whole raw accumulation) and `state/chat.ts` persists after the run guard, injecting `memoryPrompt` into the outgoing system prompt **only**. **A client tool-execution loop does exist** (`chat.ts` turns a completed `tool_call` into `executeTool` + a correlated result, no orphans; T24a declares registered tools on the wire) — so a tool-call design *is* available; earlier text here claiming otherwise predates it. `SendCtx.tools` is still only the search declaration.

## Tauri / native

- **Desktop chat streams through the shell, not the webview** (`t25`): `chat_stream` / `chat_stream_cancel` (an ipc `Channel`, status first then ordered text runs, abort on drop) behind one **transport abstraction selected by `isDesktop`** at the single chat fetch site — so a provider whose chat endpoint a webview cannot call (OpenCode Go: it 404s the CORS preflight) works on desktop, in order, cancellably. The **shared SSE parser is untouched**, so web behaviour is unchanged. **`x-opencode-session` is sent for `opencode.ai` hosts only** (value = the conversation id, so routing and prompt caching stay stable). **Known gap at the time of writing:** `Test connection` (`lib/providers/models.ts`) still fetches from the webview — the probe is the one path that does not use the transport yet.

- **App-defined `#[tauri::command]`s are NOT ACL-gated — `capabilities/default.json` needs no entry for them.** Proven two ways (T20 review): `db_set_settings`/`db_list_conversations` run from the desktop webview with no `db_*` entry in `capabilities` and no `web/src-tauri/permissions/` dir (settings + conversations exist on disk), and pinned Tauri 2.12.2 rejects an app command only when `has_app_acl_manifest` is true or the origin is non-local. **Forward risk: shipping the app's own `permissions/` manifest gating every app command — a missing entry would then fail on desktop only, while every browser stub still passes.** Only *plugin* permissions are ACL-gated.
- **Plugin native commands = `web/src-tauri/src/lib.rs`: nine (`plugin_{list,read_file,write_file,remove,data_dir}` + `plugin_fs_{read,write,list,delete}`), all through one scope helper (`resolve_within` + `safe_id`).** `plugin-data/<id>` is the **only enforced** capability; `net` is unenforceable; the rest consent-only. Never call it a sandbox.
- **Two real containment traps, both fixed once and both easy to reintroduce.** (1) `PathBuf::join`/`push` **discards the base** when the pushed path has a *prefix* (Windows `C:`), so a plugin `id` must be an **allowlist** (`[A-Za-z0-9._-]+`), never a denylist of `/ \ . ..` — mirrored in `manifestSchema.id` so a bad id fails at install. (2) Re-appending a **non-existent** suffix is not safe by itself: a *dangling* symlink makes `canonicalize` return `NotFound`, the walk treats it as a plain name and returns the symlink, and the write follows it out of the root — so check `symlink_metadata` per re-appended component.
- `resolve_within` `create_dir_all`s the root, so a *read* command creates the dir; and a `rel_path` of `""`/`"."`/`"subdir/.."` resolves to the root itself (a whole-dir delete is the plugin's own dir). Documented, not guarded.

## Release & CI

- **Version home = `web/src-tauri/tauri.conf.json` `version`** (Tauri reads it for the bundle name/version). `bun scripts/bump-version.ts <patch|minor|major|X.Y.Z>` rewrites it plus `web/src-tauri/Cargo.toml`, `web/src-tauri/Cargo.lock` (`[[package]] name = "app"`) and `web/package.json`, by targeted text replacement (never re-serialize — the JSON files are tab-indented). Runs from the repo root; `--root <dir>` overrides for tests. **A hand-bump must be followed by `bun run docs`**: `docs/reference.test.ts` pins the committed reference's `appVersion` to `web/package.json`, so the artifact is stale (and `verify` red) until regenerated — `build`/CI regenerate it as part of the build.
- **LF only** — `.gitattributes` pins `* text=auto eol=lf`. GitHub's Windows runner checks out CRLF (`core.autocrlf=true`), which made Biome diff every line and failed `bun run lint` in the release build (only the Windows job sees it).
- **Updater signing keypair — the private key IS the ability to ship updates.** Private `~/.tauri/ai-client.key` + its password `~/.tauri/ai-client.key.password` (both `600`, local only); repo secrets `TAURI_SIGNING_PRIVATE_KEY` (the key *content*, not a path) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the *public* key sits in `tauri.conf.json` `plugins.updater.pubkey` (safe to share, never regenerated once shipped — a new key orphans every installed app, since the pubkey is baked into the binary that verifies the download). Never print the private key or password, never write either into a repo file. Verify the embedded pubkey against `~/.tauri/ai-client.key.pub`. **In-app updating shipped in 0.1.2** (0.1.0 and 0.1.1 have no updater and must be replaced by hand), and the first genuine update was proven end to end: an installed 0.1.2 replaced itself with 0.2.0 in place.
- **The updater's platform key is written by tauri-action, not the CLI.** The CLI only makes the `.app.tar.gz` + `.sig`; `tauri-action`'s `upload-version-json` writes `latest.json`, mapping `macos`→`darwin`, `arm64`→`aarch64`, and a universal build publishes `darwin-aarch64`/`darwin-x86_64` (plus their `-app` variants). So pass **no `target`** to `check()`: the plugin resolves `{os}-{arch}-{installer}` then `{os}-{arch}`, and both slices already match. The docs' `macos-universal` is a custom string for a self-hosted endpoint, not what GitHub Releases carries (`updaterJsonKeepUniversal` is what would add a universal key). Android/iOS are unsupported by this plugin.
- **Release creation needs the repository's default workflow permissions set to `write`** (Settings → Actions → General). With the default at `read`, tauri-action's `POST /releases` returned `Resource not accessible by integration` even though the workflow declares `permissions: contents: write`. A run's token permissions are fixed when the run starts, so a **re-run cannot pick up a settings change — push a fresh run (delete + re-push the tag)**. `ci.yml` still pins `permissions: contents: read` for itself.
- **A `desktop-v*` tag need not be on `main`** — verified 2026-10-13: 0.3.0 was cut from a tag on the `plugin-system` branch, the workflow built and published all three platforms with **`main` untouched** (so the Vercel site kept serving the previous build), and the tap's scheduled job repinned the cask anyway because it follows **releases**, not `main`. So "release without merging" is a supported path, and a tag is the unit of release.
- **Release = `.github/workflows/release-tauri.yml`.** `workflow_dispatch` (input `bump` = patch|minor|major) runs a `version` job that bumps, commits, pushes `main`, and tags `desktop-v<version>`, then builds; a `desktop-v*` **tag push** builds only (never re-point a tag once its release is published — asset names and the release derive from it; the build job fails if the tag ≠ `tauri.conf.json`). Matrix: `macos-latest` (universal, `--target universal-apple-darwin`), `ubuntu-22.04`, `windows-latest` → `tauri-apps/tauri-action@v0` creates the GitHub Release and uploads installers.
- **Verify a published release with `bun scripts/verify-release.ts [version]`.** The version defaults to `tauri.conf.json` and the repo is read from the git remote, so nothing is kept in sync by hand; it polls (default 40 × 20s) because publishing is async. It checks what `gh release view` cannot: every installer suffix present; a `.sig` beside each updater artefact (a run that started before the signing secrets existed uploads unsigned archives no client will accept); `/releases/latest` actually being the new tag; a fetchable `latest.json`; and an entry with a signature **and a live artefact URL** for each of `darwin-aarch64`/`darwin-x86_64`/`linux-x86_64`/`windows-x86_64` — a platform with no entry never updates, silently. Exit 0 verified, 1 failed/timeout, 2 usage.
- **Builds are unsigned and not notarized — "right-click → Open" does NOT work on current macOS (user-confirmed on 27); it restricts unsigned apps further.** The only reliable install path for users is clearing the download quarantine flag: `xattr -dr com.apple.quarantine "/Applications/oss-ai-client.app"`. On Windows an unsigned installer trips SmartScreen → **More info → Run anyway**. The release body carries both — never document right-click → Open again.

- **Favicons: raster (PNG + `.ico`), never SVG-only.** Brave with **Standard Shields** and *nothing blocked* will not display an SVG favicon — Chrome shows it, and a fresh-profile Brave even fetches it (200), it just never appears in the tab; dropping the SVG for PNGs fixed it. `index.html` declares `/favicon-32.png`, `/favicon-256.png`, `/favicon.ico` and `/apple-touch-icon.png`, each with `?v=N` — **bump `?v=` whenever an icon file changes** (a browser holds a favicon per origin and does not refresh it; brave-browser#53451). Verify the server side with `agent-browser connect <port>` against a headless Brave/Chrome on a fresh `--user-data-dir` + `network requests`. `/favicon.svg` is only the artwork source, not declared. **Rasterize with `bun scripts/build-icons.ts`** (`resvg`, brew) — **never `qlmanage`**, which flattens the mark onto white: that is what put white corners on the first raster set, and an alpha *channel* (`sips -g hasAlpha`) does not prove transparency, only pixels sampled through a canvas do. `web/src-tauri/icons/*` came from that same `qlmanage` raster, so the desktop/dock icon carried the same white corners until `resvg -w 1024 -h 1024 web/public/favicon.svg web/src-tauri/app-icon.png` + `(cd web && bunx tauri icon src-tauri/app-icon.png)` regenerated the set. **`scripts/build-icons.ts` now emits `app-icon.png` itself**, the same artwork inset to Apple's grid (about 824 of 1024) by widening the viewBox, because full-bleed art is right for a favicon and reads oversized in the Dock; every platform size is derived from that one file with `tauri icon`. **Changing `icons/` does not make cargo rebuild** — `tauri dev` reuses the stale binary, so the Dock keeps the old mark until a rebuild (touch a source file or `cargo clean -p app`), and `killall Dock` if the icon cache sticks.
- **A white screen right after a push is usually the mid-deploy window, not a code fault.** The edge briefly serves the new `index.html` before its JS asset is live, so the module 404s, React never mounts, and the page is blank white (the app applies no background until it does); it clears on reload. **Check before touching code**: `agent-browser errors` against the live origin, and `document.getElementById("root")?.children.length`. `agent-browser` also has `console`.
- **The Homebrew cask lives in `JeffreyJYZ/homebrew-tap` (`Casks/oss-ai-client.rb`), and the tap repins itself.** The app self-updates, so the cask only has to point at the newest release: `.github/workflows/bump-cask.yml` **in the tap** runs on a schedule, reads this repo's newest `desktop-v*` release, downloads the universal dmg, digests it and commits version + sha256. No cross-repo token and no step in this repo's release, because the workflow only writes to its own repo. `auto_updates true` keeps Homebrew from comparing versions, so the in-app updater keeps working and `brew upgrade` never overwrites a self-updated app; Homebrew's receipt can lag the running version after one of those updates, which is cosmetic (the pin follows releases anyway, so even a forced reinstall lands the current version). Two things a user meets: casks from a third-party tap are refused until `brew trust jeffreyjyz/tap` (once per machine, casks can run code, formulae do not), and these unsigned builds still get quarantined on install, which Gatekeeper refuses, so the cask clears that attribute in its own `postflight` — Homebrew 7 has no `--no-quarantine` flag to ask for. **An app already in `/Applications` from the dmg or the in-app updater also blocks the cask: Homebrew refuses to overwrite what it does not own (`It seems there is already an App at …`), so moving to the cask needs `brew install --cask --force`, which replaces a same-or-older bundle and leaves the data in Application Support alone.**
- **Never ship a UI change tested only on the dev server** — run the production bundle (`bunx vite build && bunx vite preview`). Dev serves unbundled ESM and cannot catch bundling faults. **And never revert on a guess**: an unnecessary revert once cost a working feature, because the blame was assigned to the newest commit instead of being tested.
